## Causes and repair

The chip callback previously requested focus unconditionally after the next frame. An external TextField could receive a later pointer click before that callback and then lose focus. The callback now holds an intent generation. Outside taps, closing, and owner disable/close updates invalidate it. It checks mounting and accepts only unchanged focus, focus inside this select, or the temporary absence of primary focus during chip removal. A later external focused node prevents the callback from requesting focus. This retains the deferred request needed by Flutter web's chip-removal lifecycle rather than refocusing after arbitrary delays. Owner replacement/disposal also invalidates the old state through mounting.

The native Escape loss had a different cause. `baseline-dom-trace.json` shows that after Alpha is removed, Beta moves beneath the stationary pointer and displays the extra Flutter tooltip. Its fade-out removes the root tooltip semantics subtree and removes/reinserts the screen semantics ancestor containing INPUT. The browser then focuses BODY while the Flutter FocusNode remains focused. The DOM trace identifies the extra node's text as `Remove Beta`. Normal-motion accepting-owner removal exposes this sequence; the other combinations were controls. Source `trigger.tsx` has only an accessible remove-button label, with no tooltip. The component now uses merged button semantics with that label instead of a tooltip. `final-dom-trace.json` has no focusout after Escape and ends with query `xy`, open true. There is no DOM mutation workaround, programmatic browser focus, shared-overlay edit, or delayed Escape refocus.

Typing after Escape previously changed only the query. User input now also proposes opening when the panel is closed. Controlled open/query owners still decide the effective values. Escape retains its separate close-and-clear behavior.
